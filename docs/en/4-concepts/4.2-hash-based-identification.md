When you begin a visit with Open Data Capture, you must first chose your identification method. If you select the "Personal Information" option, you will need to complete a form with the following fields:

- First Name
- Last Name
- Sex at Birth
- Date of Birth

These data are used to compute a unique ID using a one-way hashing function to compute this ID. This method that is currently employed by the NIH for a [similar purpose](https://nda.nih.gov/nda/using-the-nda-guid.html).

:::note
When using this identification method, first and last name are never transmitted to our server. The hashing process described below is performed in your web browser.
:::

### What is a Hash?

A hash function is a mathematical function that takes an input and returns a fixed-size string of characters, which is typically a hexadecimal number. The same input will always produce the same output, but even a small change to the input will produce a very different output.

In our case, we use an algorithm called SHA-256 which creates a 256-bit (32-byte) hash value. This is considered a "strong" hash function because it's computationally infeasible to produce two different messages that have the same hash value (collision resistance) and it's also computationally infeasible to recreate the original message from its hash value (pre-image resistance). For reference, the total number of possible combinations is 1.158 x 10^77, which is a value that approaches the estimated number of atoms in the observable universe, which ranges from 10^78 to 10^82.

### Example

To illustrate how this process works, suppose we have the following information:

| Variable Name | Value      |
| ------------- | ---------- |
| First Name    | René       |
| Last Name     | Tremblay   |
| Date of Birth | 1980-01-01 |
| Sex           | female     |

Your browser first checks that every field is filled in, that the date of birth is a valid date and that the sex is "male" or "female". It then joins the first name, the last name, the date of birth (written as YYYY-MM-DD) and the sex into one string, and standardizes it:

- Letters are converted to uppercase, so letter case is ignored.
- Plain hyphens (-) are removed, so "Jean-Paul" and "JeanPaul" are the same name.
- Accented letters and ligatures are replaced by their unaccented [ASCII](https://en.wikipedia.org/wiki/ASCII) equivalents, so "René" and "Rene" are the same name, as are "Lebœuf" and "Leboeuf". Names in other scripts are converted to Latin letters, which can give two different names the same spelling: "李" and "里" both become "Li".

Nothing else is removed. Spaces, apostrophes, other dashes and all other punctuation are part of the input, so "Jean Paul" and "Jean-Paul", or "O'Brien" and "OBrien", identify two different people. A space typed at the start or end of a name counts too, although a bulk assignment file has those removed from each cell first. Enter a name the same way every time.

No secret is added to the input, so anyone who knows a person's name, date of birth and sex can compute the same identifier.

This output is used as the identifier for René Tremblay. Her first and last name are not entered into the database, and we store her date of birth and sex, alongside her identifier.

## Custom Fields

An administrator can define an instance's own identifying fields instead, for example an animal's ear tag and its cage. Staff then choose the method under the label the administrator gave it, and Start Session and the Data Hub's subject lookup ask for those fields. Every field is required. Date of birth and sex are optional, as they are for a custom identifier.

The administrator defines the fields once, under **Admin Panel** > **Instance** > **Settings**, on the **Subject Identification** tab. Each field has a label, optional help text, a pattern the value must match and an optional message shown when it does not. The values typed are never sent to the server and never stored; your browser derives the identifier from them, and a subject who returns is recognized when the same values are typed again.

On the same tab, the administrator chooses which methods staff are offered. Defining the fields does not offer them by itself; they are offered once **Offered Methods** includes them. A method that is not offered disappears from Start Session, the subject lookup and each group's default method, and a group whose default method is not offered starts on the first method that is. Turning a method off changes no subject's identifier, so it can be undone, but staff cannot start a session for the subjects it identifies until it is offered again; the page says how many subjects that is before it saves.

### How the identifier is derived

Your browser standardizes each value:

1. Letters are converted to uppercase.
2. Accents are separated from their letters, and the full-width digits and letters some keyboards produce become ordinary ones.
3. A few Latin letters that have no accent to remove are spelled out: Œ as OE, Æ as AE, Ø as O, Ł as L, Đ and Ð as D, and Þ as TH.
4. Everything that is not a letter or a digit is removed: spaces, hyphens, apostrophes and all other punctuation.

So "ab-12 34" and "AB1234" are the same value, as are "Sørensen" and "SORENSEN". Letters in other scripts are kept as they are, so "李" and "里" stay two different values. A value that has no letter or digit left is refused, and the pattern is tested against the standardized value, which holds only letters and digits, with Latin letters in uppercase.

The standardized values are then combined, in the order the fields are defined, and passed through PBKDF2 with SHA-256, 600,000 rounds and a random key, called a salt, that the instance generates when the fields are first defined. The identifier is `cf_` followed by the 64 hexadecimal characters of the result. Because of the salt, someone holding only an export of the data cannot recover a short identifier by trying every possible value, and the same values give different identifiers on two instances.

### Once a subject has been identified

The standardization, the order of the fields, the salt and the number of rounds are part of every identifier, and the values typed are not stored, so none of them can change once any subject has been identified with the fields. From then on the number and order of the fields are locked. The labels, help text, patterns and messages can still be corrected, but a label should not be repurposed: renaming "Animal ID" to "Cage number" would have staff type something else, and every returning subject would get a new identifier.
